## SC-01 회원가입

**제목**: 신규 사용자가 이메일과 비밀번호로 계정을 생성한다.

**행위자**: 비인증 사용자

**사전 조건**
- 사용자가 서비스에 가입되어 있지 않다.
- 사용자는 로그인되어 있지 않다.

**시나리오 흐름**
1. 사용자가 회원가입 페이지에 접근한다.
2. 이름, 이메일, 비밀번호를 입력한다.
3. 회원가입 버튼을 클릭한다.
4. 시스템이 이메일 중복 여부를 검증한다.
5. 시스템이 비밀번호 형식(최소 8자, 영문+숫자+특수문자)을 검증한다.
6. 시스템이 비밀번호를 bcrypt로 해시 처리한 뒤 사용자 계정을 생성한다.
7. 회원가입 완료 메시지가 표시되고, 사용자는 로그인 페이지로 이동한다.

**사후 조건**
- User 엔티티가 생성되고 계정 상태는 Active다.
- 자동 로그인은 수행되지 않는다.

**예외/대안 흐름**
- **이메일 중복**: 동일 이메일이 이미 등록된 경우 409 Conflict를 반환하고 "이미 사용 중인 이메일입니다" 메시지를 표시한다.
- **비밀번호 형식 불일치**: 조건을 충족하지 않으면 400 Bad Request와 함께 안내 메시지를 표시한다.
- **필수 항목 누락**: 이름·이메일·비밀번호 중 하나라도 비어 있으면 서버 요청 전에 클라이언트에서 차단한다.

**관련 규칙**: BR-15, F-001

## SC-02 로그인

**제목**: 가입된 사용자가 이메일과 비밀번호로 인증 토큰을 발급받는다.

**행위자**: 비인증 사용자

**사전 조건**
- 사용자 계정이 존재하고 상태가 Active다.

**시나리오 흐름**
1. 사용자가 로그인 페이지에 접근한다.
2. 이메일과 비밀번호를 입력한다.
3. 로그인 버튼을 클릭한다.
4. 시스템이 이메일로 사용자를 조회하고 비밀번호 해시를 검증한다.
5. 검증 성공 시 JWT Access Token(15분)을 응답 본문으로, Refresh Token(7일)을 HttpOnly 쿠키로 발급한다.
6. 사용자는 팀 목록 페이지로 이동한다.

**사후 조건**
- 인증 토큰이 발급되어 이후 요청에 사용된다.
- 사용자는 서비스의 모든 기능에 접근할 수 있다.

**예외/대안 흐름**
- **이메일 미존재 또는 비밀번호 불일치**: 401 Unauthorized를 반환하고 "이메일 또는 비밀번호가 올바르지 않습니다" 메시지를 표시한다. (어느 쪽이 틀렸는지 구분하지 않는다.)
- **비활성 계정**: 계정 상태가 Inactive인 경우 로그인을 거부한다.

**관련 규칙**: BR-10, F-002

## SC-03 로그아웃

**제목**: 로그인된 사용자가 인증 토큰을 무효화하고 세션을 종료한다.

**행위자**: 인증된 사용자

**사전 조건**
- 사용자가 로그인 상태다.

**시나리오 흐름**
1. 사용자가 로그아웃 버튼을 클릭한다.
2. 시스템이 서버 측에서 현재 토큰을 무효화한다.
3. 클라이언트에서 저장된 토큰을 삭제한다.
4. 사용자는 로그인 페이지로 이동한다.

**사후 조건**
- 기존 토큰은 무효화되어 재사용할 수 없다.
- 사용자는 비인증 상태로 전환된다.

**예외/대안 흐름**
- **이미 만료된 토큰으로 로그아웃 요청**: 401을 반환하되, 클라이언트는 로컬 토큰을 삭제하고 로그인 페이지로 이동한다.

**관련 규칙**: BR-10, F-002

## SC-04 팀 생성

**제목**: 로그인된 사용자가 새 팀을 생성하고 자동으로 팀장이 된다.

**행위자**: 인증된 사용자

**사전 조건**
- 사용자가 로그인 상태다.

**시나리오 흐름**
1. 사용자가 팀 목록 페이지에서 "팀 생성" 버튼을 클릭한다.
2. 팀 이름을 입력한다.
3. 생성 버튼을 클릭한다.
4. 시스템이 Team 엔티티를 생성하고, 생성자를 팀장(Leader) 역할로 UserTeamRole에 등록한다.
5. 팀 캘린더 페이지로 이동한다.

**사후 조건**
- Team 엔티티가 생성되고 상태는 Active다.
- 생성자는 해당 팀에서 팀장 역할을 가진다.

**예외/대안 흐름**
- **팀 이름 누락**: 빈 이름으로 생성 요청 시 400 Bad Request를 반환한다.

**관련 규칙**: BR-10, BR-60, F-003

## SC-05 팀원 초대 발송

**제목**: 팀장이 이메일을 입력해 팀원을 초대한다.

**행위자**: 팀장

**사전 조건**
- 사용자가 로그인 상태이고 해당 팀에서 팀장 역할을 가진다.
- 초대할 이메일의 사용자가 시스템에 가입되어 있다.

**시나리오 흐름**
1. 팀장이 팀 설정 또는 팀원 관리 페이지로 이동한다.
2. "팀원 초대" 버튼을 클릭한다.
3. 초대할 사용자의 이메일을 입력한다.
4. 초대 발송 버튼을 클릭한다.
5. 시스템이 이메일로 사용자를 조회하고 이미 팀원인지, 중복 Pending 초대가 있는지 검증한다.
6. Invitation 엔티티가 생성된다 (상태: Pending, 만료일시: 발송 후 7일).
7. 초대받은 사용자에게 INVITATION_RECEIVED 인앱 알림이 생성된다.

**사후 조건**
- Invitation 엔티티가 Pending 상태로 저장된다.
- 초대받은 사용자의 알림 목록에 미읽음 알림이 추가된다.

**예외/대안 흐름**
- **중복 Pending 초대**: 동일 팀에 동일 사용자에 대한 Pending 초대가 이미 존재하면 409 Conflict를 반환한다.
- **이미 팀 소속 사용자**: 이미 팀원인 사용자를 초대하려 하면 400 Bad Request를 반환한다.
- **미가입 이메일**: 시스템에 등록되지 않은 이메일이면 404를 반환한다.
- **팀장이 아닌 사용자가 초대 시도**: 403 Forbidden을 반환한다.

**관련 규칙**: BR-10, BR-25, BR-60, BR-90, F-005

## SC-06 초대 수락

**제목**: 초대받은 사용자가 초대를 수락하고 팀원으로 합류한다.

**행위자**: 초대받은 사용자 (인증된 사용자)

**사전 조건**
- 사용자가 로그인 상태다.
- 본인 앞으로 Pending 상태의 초대가 존재한다.
- 초대가 만료되지 않았다 (만료일시가 현재 시각 이후).

**시나리오 흐름**
1. 사용자가 알림 목록 또는 초대 목록 페이지에서 수신된 초대를 확인한다.
2. "수락" 버튼을 클릭한다.
3. 시스템이 초대 유효성을 검증한다 (Pending 상태, 만료 여부, 본인 수신 여부).
4. Invitation 상태가 Accepted로 변경된다.
5. 해당 사용자에게 팀원(Member) 역할이 UserTeamRole에 추가된다.
6. 초대를 발송한 팀장에게 INVITATION_RESPONDED 인앱 알림이 생성된다.
7. 사용자는 해당 팀의 캘린더에 접근할 수 있게 된다.

**사후 조건**
- Invitation 상태가 Accepted다.
- 사용자는 해당 팀에서 Member 역할을 가진다.
- 팀장의 알림 목록에 미읽음 알림이 추가된다.

**예외/대안 흐름**
- **만료된 초대**: 만료일시가 지난 초대 수락 시도 시 400 Bad Request와 "초대가 만료되었습니다" 메시지를 반환한다.
- **이미 응답한 초대**: Accepted 또는 Declined 상태의 초대에 재응답 시도 시 409 Conflict를 반환한다.
- **본인 초대가 아닌 경우**: 403 Forbidden을 반환한다.

**관련 규칙**: BR-10, BR-25, BR-90, F-006

## SC-08 월간 캘린더 조회

**제목**: 팀 소속 사용자가 월 단위로 팀의 일정을 조회한다.

**행위자**: 팀 소속 사용자 (팀장 또는 팀원)

**사전 조건**
- 사용자가 로그인 상태이고 해당 팀에 소속되어 있다.

**시나리오 흐름**
1. 사용자가 팀을 선택하고 캘린더 페이지에 접근한다.
2. 월간 뷰가 기본으로 표시된다.
3. 시스템이 해당 팀의 해당 월 일정 목록을 반환한다.
4. 각 날짜 셀에 해당 날짜의 일정 제목이 표시된다.
5. 사용자가 이전/다음 월 이동 버튼을 클릭하면 해당 월의 일정을 새로 조회한다.

**사후 조건**
- 선택한 월의 팀 일정이 캘린더 뷰에 표시된다.

**예외/대안 흐름**
- **팀 미소속 사용자의 접근**: 403 Forbidden을 반환한다.
- **일정이 없는 월**: 빈 캘린더가 표시된다 (오류 아님).

**관련 규칙**: BR-10, BR-60, F-014

## SC-09 주간 캘린더 조회

**제목**: 팀 소속 사용자가 주 단위로 팀의 일정을 조회한다.

**사전 조건**
- 사용자가 로그인 상태이고 해당 팀에 소속되어 있다.

**시나리오 흐름**

3. 요일별로 일정이 시간대 순서로 표시된다.
4. 사용자가 이전/다음 주 이동 버튼을 클릭하면 해당 주의 일정을 새로 조회한다.

**사후 조건**
- 선택한 주의 팀 일정이 주간 뷰에 표시된다.

**예외/대안 흐름**
- **팀 미소속 사용자의 접근**: 403 Forbidden을 반환한다.

**관련 규칙**: BR-10, BR-60, F-015

## SC-10 날짜 선택 후 일일 뷰 조회

**제목**: 사용자가 캘린더에서 특정 날짜를 선택하면 해당 날짜의 일정과 채팅이 함께 표시된다.

**행위자**: 팀 소속 사용자 (팀장 또는 팀원)

**사전 조건**
- 사용자가 로그인 상태이고 해당 팀에 소속되어 있다.

**시나리오 흐름**
1. 사용자가 월간 또는 주간 캘린더에서 특정 날짜를 클릭한다.
2. 클라이언트가 두 요청을 병렬로 호출한다:
   - `GET /teams/{teamId}/schedules?weekStart=YYYY-MM-DD&weekEnd=YYYY-MM-DD` (해당 날짜 포함 주간 범위)
   - `GET /teams/{teamId}/chats/{date}/messages` (해당 날짜 채팅 이력)
3. 화면 좌측에는 해당 날짜의 일정 목록이, 우측에는 채팅 메시지 목록이 표시된다.

**사후 조건**
- 선택한 날짜의 일정과 채팅 이력이 단일 화면에 표시된다.

**예외/대안 흐름**
- **일정과 채팅 모두 없는 날짜**: 빈 목록이 표시된다.
- **팀 미소속 사용자의 접근**: 403 Forbidden을 반환한다.

**관련 규칙**: BR-10, BR-40, BR-50, BR-60, F-016, F-018

## SC-11 일정 생성

**제목**: 팀장이 팀의 일정을 새로 생성한다.

**행위자**: 팀장

**사전 조건**
- 사용자가 로그인 상태이고 해당 팀에서 팀장 역할을 가진다.

**시나리오 흐름**
1. 팀장이 캘린더 페이지에서 "일정 추가" 버튼을 클릭하거나 날짜 셀을 선택한다.
2. 일정 생성 폼이 표시된다.
3. 제목, 시작일시, 종료일시를 입력한다. 담당자는 선택 사항으로 팀 소속 팀원 중에서 지정한다.
4. 저장 버튼을 클릭한다.
5. 시스템이 입력값을 검증한다 (제목 필수, 종료일시 >= 시작일시, 담당자 소속 여부).
6. Schedule 엔티티가 생성된다 (상태: Scheduled).
7. 캘린더에 새 일정이 반영된다.

**사후 조건**
- Schedule 엔티티가 Scheduled 상태로 저장된다.
- 생성자(팀장)가 작성자로 기록된다.

**예외/대안 흐름**
- **제목 누락**: 400 Bad Request를 반환한다.
- **종료일시가 시작일시보다 이전**: 400 Bad Request와 "종료 시간은 시작 시간과 같거나 이후여야 합니다" 메시지를 반환한다.
- **비소속 사용자를 담당자로 지정**: 400 Bad Request를 반환한다.
- **팀원이 일정 생성 시도**: 403 Forbidden을 반환한다.

**관련 규칙**: BR-10, BR-20, BR-70, BR-75, F-010

## SC-12 일정 수정

**제목**: 팀장이 기존 일정의 정보를 변경한다.

**행위자**: 팀장

**사전 조건**
- 사용자가 로그인 상태이고 해당 팀에서 팀장 역할을 가진다.
- 수정할 일정이 존재한다.

**시나리오 흐름**
1. 팀장이 캘린더에서 수정할 일정을 클릭한다.
2. 일정 상세 또는 수정 폼이 표시된다.
3. 제목, 시작일시, 종료일시, 담당자 등 원하는 항목을 변경한다.
4. 저장 버튼을 클릭한다.
5. 시스템이 입력값을 검증한다 (종료일시 >= 시작일시, 담당자 소속 여부).
6. Schedule 엔티티가 갱신된다.
7. 변경 내용이 캘린더에 반영된다.

**사후 조건**
- Schedule 엔티티의 변경 내용이 저장된다.

**예외/대안 흐름**
- **종료일시가 시작일시보다 이전**: 400 Bad Request를 반환한다.
- **비소속 사용자를 담당자로 지정**: 400 Bad Request를 반환한다.
- **팀원이 일정 수정 시도**: 403 Forbidden을 반환한다.
- **동시 편집 충돌**: 낙관적 잠금이 적용되어 있는 경우 409 Conflict를 반환하고, 사용자에게 최신 내용 확인을 안내한다.

**관련 규칙**: BR-10, BR-20, BR-70, BR-75, F-011

## SC-13 일정 삭제

**제목**: 팀장이 팀의 일정을 삭제한다.

**행위자**: 팀장

**사전 조건**
- 사용자가 로그인 상태이고 해당 팀에서 팀장 역할을 가진다.
- 삭제할 일정이 존재한다.

**시나리오 흐름**
1. 팀장이 캘린더에서 삭제할 일정을 클릭한다.
2. "삭제" 버튼을 클릭한다.
3. 확인 다이얼로그가 표시된다.
4. 확인을 클릭한다.
5. 시스템이 Schedule 엔티티를 삭제한다.
6. 캘린더에서 해당 일정이 제거된다.

**사후 조건**
- Schedule 엔티티가 삭제된다.
- 캘린더에 더 이상 표시되지 않는다.

**예외/대안 흐름**
- **팀원이 일정 삭제 시도**: 403 Forbidden을 반환한다.
- **이미 삭제된 일정에 접근**: 404 Not Found를 반환한다.

**관련 규칙**: BR-10, BR-20, F-012

## SC-14 채팅 메시지 전송

**제목**: 팀 소속 사용자가 특정 날짜의 채팅방에 메시지를 전송한다. 팀원은 이를 통해 일정 변경을 요청할 수 있다.

**행위자**: 팀 소속 사용자 (팀장 또는 팀원)

**사전 조건**
- 사용자가 로그인 상태이고 해당 팀에 소속되어 있다.
- 일일 뷰(SC-10)에서 특정 날짜가 선택된 상태다.

**시나리오 흐름**
1. 사용자가 일일 뷰 우측 채팅 영역에서 메시지를 입력한다.
   - 예: "스프린트 회의를 13시로 변경할 수 있을까요?"
2. 전송 버튼을 클릭하거나 Enter를 입력한다.
3. 시스템이 메시지 내용을 검증한다 (빈 문자열, 공백만인 경우 차단).
4. Message 엔티티가 저장된다 (`{ messageId, content, createdAt }` 포함 201 Created 반환).
5. 해당 날짜의 채팅방에 메시지가 즉시 표시된다.
6. 팀원이 전송한 경우, 해당 팀의 모든 팀장에게 MESSAGE_RECEIVED 인앱 알림이 생성된다.

**사후 조건**
- Message 엔티티가 (팀 + 기준 날짜) 단위 채팅방에 저장된다.
- 메시지는 수정·삭제할 수 없다.
- 팀원이 전송한 경우 팀장의 알림 목록에 미읽음 알림이 추가된다.

**예외/대안 흐름**
- **빈 메시지 또는 공백만 입력**: 400 Bad Request를 반환하고 전송을 차단한다.
- **팀 미소속 사용자**: 403 Forbidden을 반환한다.
- **메시지 수정·삭제 시도**: 405 Method Not Allowed를 반환한다.

**관련 규칙**: BR-10, BR-30, BR-35, BR-50, BR-60, BR-85, BR-90, F-017

## SC-15 알림 조회 및 읽음 처리

**제목**: 사용자가 본인의 알림 목록을 조회하고 읽음 처리한다.

**행위자**: 인증된 사용자

**사전 조건**
- 사용자가 로그인 상태다.

**시나리오 흐름**

**[알림 조회]**
1. 사용자가 알림 아이콘을 클릭한다. 아이콘에는 미읽음 알림 수가 배지로 표시된다.
2. 시스템이 해당 사용자의 모든 알림 목록을 반환한다 (생성일시 내림차순).
3. 알림 유형(MESSAGE_RECEIVED / INVITATION_RECEIVED / INVITATION_RESPONDED)과 읽음 여부가 표시된다.

**[단건 읽음 처리]**
4. 사용자가 특정 알림을 클릭한다.
5. 시스템이 해당 알림의 읽음 여부를 Read로 변경한다.
6. 미읽음 배지 카운트가 감소한다.
7. 알림 유형에 따라 관련 화면(채팅 또는 초대 목록)으로 이동한다.

**사후 조건**
- 읽음 처리된 알림의 상태가 Read로 저장된다.
- 알림은 삭제되지 않는다.

**예외/대안 흐름**
- **본인 알림이 아닌 것을 읽음 처리 시도**: 403 Forbidden을 반환한다.
- **알림이 없는 경우**: 빈 목록을 반환한다 (오류 아님).

**관련 규칙**: BR-10, BR-90, F-019, F-020
