# Team CalTalk 도메인 정의서

> **버전**: v0.4 | **최초 작성**: 2026-05-04 | **최종 수정**: 2026-05-04

---

## 1. 서비스 개요
ff
팀 단위 캘린더 기반 일정관리와 채팅을 통합한 협업 애플리케이션.  
팀장은 일정을 관리하고, 팀원은 채팅으로 일정 변경을 요청하며, 모든 대화는 날짜별로 맥락이 유지된다.

---

## 2. 핵심 도메인 개념

### 2.1 사용자 (User)

| 속성 | 설명 |
|------|------|
| 식별자 | 고유 ID |
| 이름 | 표시 이름 |
| 이메일 | 로그인 계정 (중복 불가) |
| 비밀번호 | 해시 저장 |
| 계정 상태 | 활성(Active) / 비활성(Inactive) |

- 모든 사용자는 인증(로그인) 후에만 서비스를 이용할 수 있다.
- 역할은 팀 단위로 부여된다. `UserTeamRole(사용자, 팀, 역할)` 관계로 표현되며, 동일 사용자가 팀마다 다른 역할(팀장/팀원)을 가질 수 있다.

**팀 내 역할 (Role)**

| 역할 | 설명 |
|------|------|
| 팀장 (Leader) | 팀 일정 생성·수정·삭제 권한 보유 |
| 팀원 (Member) | 팀 일정 조회만 가능, 변경은 채팅으로 요청 |

---

### 2.2 팀 (Team)

| 속성 | 설명 |
|------|------|
| 식별자 | 고유 ID |
| 이름 | 팀 이름 |
| 삭제 상태 | 활성(Active) / 삭제됨(Deleted) — 소프트 삭제 |

- 팀을 생성한 사용자가 최초 팀장이 된다.
- 팀은 최소 1명의 팀장으로 구성되며, 팀원은 0명 이상이다.
- 팀 일정과 채팅은 팀 단위로 격리된다.
- 삭제된 팀(Deleted)의 데이터는 보존되며, 새 접근 요청에 대해서만 차단한다.
- 관계: Team 1 ↔ N UserTeamRole, Team 1 ↔ N Schedule, Team 1 ↔ N Chat, Team 1 ↔ N Invitation

---

### 2.3 초대 (Invitation)

팀원을 초대하는 행위를 별도 엔티티로 표현한다. 초대 수락 전까지 팀 접근 권한이 부여되지 않는다.

| 속성 | 설명 |
|------|------|
| 식별자 | 고유 ID |
| 소속 팀 | 팀 참조 |
| 초대한 팀장 | 발신 사용자 |
| 초대받은 사용자 | 수신 사용자 |
| 상태 | 대기(Pending) / 수락(Accepted) / 거절(Declined) / 만료(Expired) |
| 생성일시 | 초대 발송 시각 |
| 만료일시 | 초대 유효 기한 (기본값: 발송 후 7일) |

- 동일 팀에 동일 사용자에 대한 Pending 초대가 이미 존재하면 중복 초대를 생성할 수 없다.
- 초대 수락 시 해당 사용자에게 팀원(Member) 역할이 자동 부여된다.
- 관계: Invitation N ↔ 1 Team

---

### 2.4 일정 (Schedule)

| 속성 | 설명 |
|------|------|
| 식별자 | 고유 ID |
| 제목 | 일정 이름 (최소 1자) |
| 시작일시 | 일정 시작 날짜·시간 |
| 종료일시 | 일정 종료 날짜·시간 (시작일시와 같거나 이후) |
| 상태 | 예정(Scheduled) / 완료(Done) / 취소(Cancelled) |
| 담당자 | 해당 팀 소속 팀원(들), 0명 이상 |
| 소속 팀 | 팀 참조 |
| 작성자 | 생성한 팀장 |

**일정 상태 전이**

| 현재 상태 | 전이 가능 상태 | 전이 주체 |
|-----------|--------------|----------|
| Scheduled | Done, Cancelled | 팀장 (수동) |
| Done | Scheduled | 팀장 (수동) |
| Cancelled | Scheduled | 팀장 (수동) |

**일정 권한 규칙**

| 행위 | 팀장 | 팀원 |
|------|------|------|
| 일정 조회 | ✅ | ✅ |
| 일정 생성 | ✅ | ❌ |
| 일정 수정/삭제 | ✅ | ❌ |
| 상태 변경 | ✅ | ❌ |
| 일정 변경 요청 | — | ✅ (채팅으로) |

---

### 2.5 채팅 (Chat)

| 속성 | 설명 |
|------|------|
| 식별자 | 고유 ID |
| 기준 날짜 | 사용자가 캘린더에서 선택한 날짜 (*) |
| 소속 팀 | 팀 참조 |

> (*) 캘린더와 대화의 맥락 공유를 위해 날짜 단위로 채팅방을 분리. 메시지 전송 시각의 날짜와 다를 수 있다.

**메시지 (Message)**

| 속성 | 설명 |
|------|------|
| 식별자 | 고유 ID |
| 작성자 | 발신 사용자 |
| 내용 | 자유 텍스트 (최소 1자, 일정 변경 요청 포함) |
| 작성일시 | 전송 시각 |

- 채팅은 (팀 + 기준 날짜) 조합으로 하나의 채팅방을 구성한다.
- 채팅은 자유 텍스트 채널이며, 시스템이 요청을 자동 파싱하거나 일정과 연결하지 않는다. 팀장이 채팅을 보고 직접 일정을 수정한다.
- 전송된 메시지는 수정·삭제할 수 없다 (불변성 보장).
- 관계: Chat N ↔ 1 Team, Chat 1 ↔ N Message

---

### 2.6 알림 (Notification)

팀원이 채팅으로 일정 변경을 요청했을 때 팀장이 인지할 수 있도록 인앱(In-app) 알림을 제공한다.  
외부 채널(이메일, 푸시)은 v1 범위 외로 제외한다.

| 속성 | 설명 |
|------|------|
| 식별자 | 고유 ID |
| 수신자 | 알림을 받을 사용자 |
| 유형 | 메시지_수신(MESSAGE_RECEIVED) / 초대_수신(INVITATION_RECEIVED) / 초대_응답(INVITATION_RESPONDED) |
| 참조 ID | 원인이 된 엔티티 ID (Message 또는 Invitation) |
| 읽음 여부 | boolean (true: 읽음 / false: 미읽음) |
| 생성일시 | 알림 발생 시각 |

- 알림은 수신자 본인만 읽음 처리할 수 있다.
- 알림 삭제는 지원하지 않는다. 읽음 처리로 관리한다.
- 관계: Notification N ↔ 1 User

## 3. 핵심 비즈니스 규칙

각 규칙에는 검증 조건(Given / When / Then)을 함께 명시한다.

| # | 규칙 | 검증 조건 | 관련 UC |
|---|------|-----------|---------|
| BR-10 | **인증 필수** — 로그인하지 않은 사용자는 어떤 기능도 사용할 수 없다. | Given 미인증 사용자 / When 임의 API 호출 / Then 401 Unauthorized 반환 | UC-01 |
| BR-15 | **회원가입 유일성** — 이메일은 시스템 전역에서 중복될 수 없다. | Given 기존 이메일로 회원가입 시도 / When POST /auth/register / Then 409 Conflict 반환 | UC-00 |
| BR-20 | **일정 수정 권한** — 팀 일정은 팀장만 생성·수정·삭제·상태 변경할 수 있다. | Given 팀원 계정 / When 일정 생성·수정·삭제·상태 변경 시도 / Then 403 Forbidden 반환 | UC-05, UC-06 |
| BR-25 | **초대 중복 방지** — 동일 팀에 동일 사용자에 대한 Pending 초대가 이미 존재하면 추가 초대를 생성할 수 없다. | Given Pending 초대 존재 / When 동일 대상에 재초대 시도 / Then 409 Conflict 반환 | UC-03 |
| BR-30 | **변경 요청 흐름** — 팀원이 일정 변경을 원할 경우 채팅으로 자유 텍스트 요청하고, 팀장이 판단 후 직접 수정한다. 시스템은 요청을 자동 처리하지 않는다. | Given 팀원 / When 채팅 메시지 전송 / Then `{ messageId, content, createdAt }` 포함 201 Created 반환 | UC-07 |
| BR-35 | **메시지 불변성** — 전송된 메시지는 수정하거나 삭제할 수 없다. | Given 작성자 또는 팀장 / When 메시지 수정·삭제 시도 / Then 405 Method Not Allowed 반환 | UC-08 |
| BR-40 | **채팅-일정 연동** — 날짜 선택 시 해당 날짜의 일정 목록(월/주 캘린더 조회)과 채팅 이력(날짜별 채팅 조회)을 함께 화면에 표시한다. 클라이언트가 각각 `GET /teams/{teamId}/schedules` 및 `GET /teams/{teamId}/chats/{date}/messages`를 조합하여 렌더링한다. | Given 인증된 사용자 / When 특정 날짜 선택 / Then 해당 날짜의 일정 목록과 채팅 메시지 목록이 화면에 함께 표시됨 | UC-04, UC-08 |
| BR-50 | **날짜별 채팅 이력** — 채팅 메시지는 (팀 + 기준 날짜) 단위로 귀속된다. | Given 팀 + 날짜 / When 채팅 조회 / Then 해당 팀·날짜의 메시지만 반환 | UC-08 |
| BR-60 | **팀 격리** — 일정과 채팅은 팀 단위로 격리되며, 소속되지 않은 팀 데이터에 접근할 수 없다. | Given 팀A 소속 사용자 / When 팀B 일정·채팅 조회 시도 / Then 403 Forbidden 반환 | UC-02~UC-08 전체 |
| BR-70 | **일정 시간 무결성** — 일정의 종료일시는 시작일시와 같거나 이후여야 한다. | Given 팀장 / When 종료일시 < 시작일시인 일정 저장 시도 / Then 400 Bad Request 반환 / 경계값: 종료일시 == 시작일시이면 허용 | UC-05, UC-06 |
| BR-75 | **담당자 소속 검증** — 일정 담당자로 지정할 수 있는 사용자는 해당 팀의 현재 소속 팀원이어야 한다. 팀을 탈퇴하거나 제거된 사용자는 담당자 목록에서 자동 제거된다. | Given 팀장 / When 비소속 사용자를 담당자로 지정 시도 / Then 400 Bad Request 반환; 팀원 제거 시 해당 사용자가 담당자인 일정에서 자동 제거 | UC-03, UC-05, UC-06 |
| BR-80 | **팀장 최소 인원** — 팀에 팀장이 1명뿐인 경우, 해당 팀장의 역할을 제거하거나 팀장을 팀원으로 강등할 수 없다. | Given 팀장 1명 팀 / When 해당 팀장 역할 제거 또는 팀원으로 변경 시도 / Then 409 Conflict 반환 | UC-03 |
| BR-85 | **메시지 내용 필수** — 채팅 메시지 내용은 빈 문자열(공백 포함)을 허용하지 않는다. | Given 인증된 사용자 / When 빈 문자열 또는 공백만으로 구성된 내용으로 메시지 전송 시도 / Then 400 Bad Request 반환 | UC-07, UC-08 |
| BR-90 | **알림 자동 생성** — 팀원이 메시지를 전송하면 해당 팀의 모든 팀장에게 MESSAGE_RECEIVED 알림이 생성된다. 초대 발송 시 수신자에게 INVITATION_RECEIVED, 초대 응답 시 발신 팀장에게 INVITATION_RESPONDED 알림이 생성된다. | Given 메시지 저장 성공 / When 트랜잭션 완료 / Then 팀장(들)의 알림 목록에 Unread 알림 생성 | UC-07, UC-03 |

## 5. 도메인 경계 (Bounded Context)

```
┌──────────────────────────────────────────────────────┐
│                   Team CalTalk                       │
│                                                      │
│  ┌──────────┐       ┌──────────────┐                 │
│  │  인증    │──────►│    팀 관리   │                 │
│  │ (Auth)   │       │   (Team)     │                 │
│  └──────────┘       └──────┬───────┘                 │
│                            │ 팀·역할 제공             │
│             ┌──────────────┼──────────────┐          │
│             ▼              ▼              │          │
│       ┌──────────┐   ┌──────────────┐    │          │
│       │  일정    │◄─►│    채팅      │    │          │
│       │(Schedule)│   │   (Chat)     │    │          │
│       └──────────┘   └──────┬───────┘    │          │
│                             │ 이벤트 발행 │          │
│                             ▼            │          │
│                      ┌──────────────┐   │          │
│                      │    알림      │   │          │
│                      │(Notification)│   │          │
│                      └──────────────┘   │          │
└──────────────────────────────────────────────────────┘
```

**컨텍스트 간 인터페이스**

| 출발 컨텍스트 | 도착 컨텍스트 | 전달 내용 |
|--------------|--------------|-----------|
| Auth | 전체 | 인증된 사용자 ID 및 팀 내 역할 |
| Team | Schedule | 팀 소속 여부 및 역할 (권한 검증용) |
| Team | Chat | 팀 소속 여부 (접근 제어용) |
| Team | Notification | 초대 발송/응답 이벤트 |
| Schedule | Chat | 날짜 선택 시 해당 날짜의 일정 목록(`schedules[]`) 제공 |
| Chat | Schedule | 팀장이 채팅 검토 후 일정 수정 트리거 (수동) |
| Chat | Notification | 메시지 저장 완료 이벤트 → 팀장 알림 생성 |

## 7. 비기능 요건 (도메인 제약)

도메인 정의 단계에서 아키텍처와 설계 결정에 영향을 미치는 비기능 제약사항을 명시한다.

| 구분 | 항목 | 요건 |
|------|------|------|
| 보안 | 인증 토큰 | JWT 또는 세션 기반 인증. 토큰 만료 후 재발급 필요. 로그아웃 시 서버 측 무효화 처리 필요. |
| 보안 | 비밀번호 저장 | bcrypt 등 단방향 해시 알고리즘 사용 필수. 평문 저장 금지. |
| 보안 | 팀 격리 | 모든 API 레이어에서 팀 소속 검증 수행. 팀 ID를 URL 파라미터로 받는 경우 반드시 소속 여부 확인. |
| 성능 | 날짜별 조회 | 채팅 메시지 및 일정 조회는 (팀 ID + 기준 날짜) 복합 인덱스 필요. |
| 성능 | 알림 조회 | 미읽음 알림 수 표시를 위한 카운트 쿼리 최적화 고려 (읽음 여부 인덱스). |
| 확장성 | 팀 규모 | 단일 팀의 팀원 수 상한을 정의해야 함 (미결). 현재 제약 없음. |
| 데이터 | 메시지 보존 | 메시지는 삭제되지 않으므로 날짜가 오래된 채팅방의 아카이빙 정책 검토 필요 (v2 이후). |
