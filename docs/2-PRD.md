## 2. 배경 및 문제 정의

### 2.1 시장 배경

팀 단위 협업 도구 시장에는 Google Calendar(캘린더), Slack(메신저), Asana(프로젝트 관리) 등이 존재하지만, 이들은 각각 분리된 인터페이스에서 작동한다. 특히 **소규모 팀의 일정 조율 시 다음 문제 발생**:

1. **맥락 단절**: 캘린더에서 일정을 확인하고, 메신저에서 변경을 요청하면서 맥락이 분산됨
2. **의사결정 지연**: 팀장이 여러 채널을 확인해야 하므로 일정 변경 요청에 대한 응답이 늦음
3. **변경 이력 관리**: 구두 또는 산발적 메시지로 일정이 변경되면서 감시·감시(Audit) 불가능

### 2.2 기회 인식

Team CalTalk는 **캘린더 중심의 협업 공간**으로서:
- 일정과 채팅을 하나의 화면에서 통합 제공
- 날짜별 맥락 유지로 변경 요청과 의사결정을 같은 공간에서 해결
- 모든 팀 구성원이 동일한 상태를 공유

### 2.3 해결하려는 핵심 문제

| 문제 | Team CalTalk의 해결책 |
|------|---------------------|
| 일정 조회와 변경 요청 채널 분산 | 날짜별 캘린더 + 채팅 통합 UI |
| 팀장의 의사결정 지연 | 인앱 알림으로 즉시 인지 |
| 변경 이력 불명확 | 채팅 메시지는 불변성 보장으로 감사 추적 가능 |
| 팀 멤버 추가 복잡성 | 초대 기반 멤버 관리로 권한 자동 부여 |

## 3. 서비스 목표

### 3.1 사용자 목표

**팀장 (Leader)**
- 팀의 모든 일정을 한 곳에서 관리 (조회/생성/수정/삭제)
- 팀원의 변경 요청을 날짜별 채팅으로 수신하고 즉시 피드백
- 팀 구성원을 초대하고 역할을 관리

**팀원 (Member)**
- 팀의 일정을 캘린더로 확인
- 변경이 필요하면 채팅으로 자유롭게 요청
- 팀장의 의사결정을 알림으로 인지

### 3.2 비즈니스 목표

- **보유자 확보**: 첫 3개월 50개 팀 이상 가입
- **활성 사용률**: 월간 활성 사용자(MAU) 대비 주 2회 이상 사용 비율 60% 이상
- **팀 유지율**: 가입 후 1개월 팀 유지율 85% 이상
- **자연 성장**: 팀 확대 시 팀원 초대 경험으로 구전 유도

### 3.3 제품 원칙

| 원칙 | 설명 |
|------|------|
| 단순성 | 일정 + 채팅 2가지 핵심 기능에 집중. 복잡한 자동화 제공하지 않음 |
| 팀 격리 | 팀별 데이터는 완전 격리. 팀원은 팀에 초대되기 전까지 접근 불가 |
| 감시(Audit) | 채팅 메시지는 삭제 불가, 모든 변경 이력 추적 |
| 빠른 의사결정 | 팀장이 별도 조회 없이 알림으로 요청 인지 후 즉시 조치 |

## 4. 사용자 페르소나

### 페르소나 1: 팀장 — 김인선 (Product Manager)

| 항목 | 내용 |
|------|------|
| 역할 | 5명 프로덕션 팀의 팀장 |
| 목표 | 팀 일정을 체계적으로 관리하고 팀원의 변경 요청을 빠르게 처리 |
| 주요 행동 | 스프린트 계획, 회의실 예약, 마감일 설정; 메시지로 요청 받으면 즉시 반영 |
| 통증점 | Slack 메시지 놓침, Google Calendar에 일정은 있지만 메시지는 다른 곳에 있음, 변경 의도 파악 어려움 |
| 선호 | 한 화면에서 모든 정보 확인; 실시간 알림 |

### 페르소나 2: 팀원 — 이준호 (Engineer)

| 항목 | 내용 |
|------|------|
| 역할 | 팀의 개발자 |
| 목표 | 일정을 확인하고, 변경이 필요하면 간단히 요청 |
| 주요 행동 | 일일 캘린더 확인, 회의 예약 확인; 작업 지연 시 일정 변경 요청 |
| 통증점 | 팀장에게 "일정 변경 가능?" 메시지를 보냈는데 응답 없음; 최종 결과를 모름 |
| 선호 | 간단한 UI, 빠른 응답 시간, 명확한 최종 상태 |

## 6. MVP 범위

### 6.1 MVP에 포함할 것 (v1.0)

**핵심 시나리오**: 팀장이 팀을 생성하고, 팀원을 초대한 후, 팀원과 함께 일정을 관리하고 채팅으로 변경을 논의

| 항목 | 범위 |
|------|------|
| **사용자** | 회원가입, 로그인/로그아웃 |
| **팀 관리** | 팀 생성, 팀 조회, 팀원 초대, 초대 수락/거절 |
| **일정** | 일정 생성/수정/삭제, 월/주/일 캘린더 뷰 |
| **채팅** | 날짜별 채팅방, 메시지 전송/조회 |
| **알림** | 팀원 메시지 시 팀장에게 인앱 알림 |
| **플랫폼** | 웹 애플리케이션 (데스크톱·태블릿) |
| **백엔드 런타임** | Node.js LTS + TypeScript (strict) |
| **백엔드 프레임워크** | Express.js |
| **ORM / 마이그레이션** | Prisma (TypeScript 네이티브, Prisma Migrate 내장) |
| **데이터 저장소** | PostgreSQL |
| **인증** | JWT(HS256), Access Token 15분 / Refresh Token 7일 |
| **입력 검증** | zod 스키마 (API 레이어 런타임 검증) |
| **로깅** | pino (JSON 구조화 로깅) |
| **보안 헤더** | helmet |
| **속도 제한** | express-rate-limit |
| **프론트엔드 빌드** | Vite |
| **프론트엔드 프레임워크** | React 18 + TypeScript |
| **라우팅** | React Router v6 |
| **서버 상태** | TanStack Query (React Query v5) |
| **클라이언트 상태** | Zustand (인증 정보, 선택된 팀) |
| **HTTP 클라이언트** | Axios |
| **백엔드 테스트** | Jest + Supertest + Testcontainers |
| **프론트엔드 테스트** | Vitest + React Testing Library |

## 7. 주요 사용자 흐름 (User Flow)

### 흐름 1: 팀 생성 및 팀원 초대

```
사용자 (비인증)
  ↓
① 회원가입 (이메일, 비밀번호)
  ↓ (User 엔티티 생성, 상태: Active)
② 로그인
  ↓ (세션/토큰 발급)
③ "팀 생성" 버튼 클릭
  ↓ (팀 이름 입력)
④ 팀 생성 완료
  ↓ (사용자 = 팀장 등록)
⑤ 팀 조회 페이지 → "팀원 초대" 클릭
  ↓ (팀원 이메일 입력)
⑥ 초대 발송 (Invitation 상태: Pending)
  ↓ (초대받은 사용자에게 INVITATION_RECEIVED 알림)
⑦ 초대받은 사용자 → 알림 클릭 → 수락
  ↓ (Invitation 상태: Accepted)
⑧ 발신 팀장에게 INVITATION_RESPONDED 알림
  ↓
초대 완료, 팀원이 팀에 속함
```

**참고**: BR-10, BR-25, BR-90 적용

---

### 흐름 2: 일일 일정 확인 및 팀원의 변경 요청

```
팀원 (인증된 팀원)
  ↓
① 캘린더 페이지 접근
  ↓ (월/주 뷰에서 팀의 모든 일정 조회)
② 특정 날짜(예: 2026-05-10) 클릭
  ↓
③ 일일 상세 뷰 표시
  - 좌측: 2026-05-10의 일정 목록
    * "스프린트 회의" (09:00-10:00)
    * "고객 미팅" (14:00-15:00)
  - 우측: 2026-05-10 채팅방
  ↓ (메시지 로드)
④ 팀원이 채팅에 메시지 입력
  - "스프린트 회의를 13시로 변경할 수 있을까요?"
  ↓ (F-017: 메시지 전송)
⑤ 메시지 저장 (Message 엔티티 생성)
  ↓ (BR-90 적용: 팀장(들)에게 MESSAGE_RECEIVED 알림 발행)
⑥ 팀장 → 알림 수신
  ↓ (Notification 상태: Unread)
⑦ 팀장이 알림 클릭 → 동일 날짜의 채팅 이동
  ↓
⑧ 팀장이 메시지 확인 후 일정 수정
  - "스프린트 회의" 시간을 09:00-10:00 → 13:00-14:00 변경
  ↓ (F-011 실행, BR-70 검증: 종료 시간 ≥ 시작 시간)
⑨ 일정 업데이트 완료
  ↓
⑩ 팀원은 캘린더 새로고침 → 변경된 일정 확인
```

**참고**: UC-04, UC-07, UC-08, BR-30, BR-40, BR-50, BR-60 적용

### 흐름 3: 팀원 제거 후 담당 일정 처리

```
팀장 (팀장)
  ↓
① 팀 설정 → "팀 멤버" 탭
  ↓ (현재 팀원 목록)
② 제거 대상 팀원 선택 → "제거" 버튼
  ↓ (F-008 실행)
③ 제거 확인
  ↓
④ 시스템 처리
  - 해당 사용자를 팀에서 제거 (UserTeamRole 삭제)
  - BR-75 적용: 해당 사용자가 담당자로 지정된 모든 일정에서 제거
    예) "프로젝트 A - 이준호 담당" → "담당자: (없음)" 또는 다른 팀원으로 재할당
  ↓
⑤ 완료
```

## 8. 비기능 요건

### 8.1 실시간 통신 방식

채팅 메시지의 실시간 수신은 **Long Polling** 방식으로 구현한다. WebSocket은 배포 환경(로드밸런서, 프록시 등)에서 별도 설정이 필요하고 연결 유지 비용이 크므로, 소규모 팀 대상의 v1에서는 Long Polling으로 충분하다.

| 항목 | 사양 |
|------|------|
| **방식** | HTTP Long Polling (WebSocket 미사용) |
| **폴링 엔드포인트** | `GET /teams/{teamId}/chats/{date}/messages?after={lastMessageId}` |
| **서버 대기 시간** | 새 메시지가 없으면 최대 20초 대기 후 빈 응답 반환 |
| **클라이언트 재요청** | 응답 수신 즉시(빈 응답 포함) 다음 요청 재전송 |
| **타임아웃 처리** | 네트워크 오류 시 3초 후 재시도, 최대 3회 |
| **v2 전환 기준** | 팀 규모 확대 또는 메시지 지연 문제 발생 시 WebSocket으로 전환 검토 |

### 8.2 성능

| 요건 | 상세 | 목표 |
|------|------|------|
| **API 응답 시간** | 일반 조회(월/주/일 캘린더, 채팅) | p95: 500ms 이하 |
| **API 응답 시간** | 일정 생성/수정/삭제 | p95: 800ms 이하 |
| **Long Polling 응답** | 새 메시지 존재 시 즉시 반환, 없으면 최대 20초 대기 | p95: 21초 이하 |
| **DB 인덱스** | (팀 ID, 기준 날짜) 복합 인덱스 | 채팅·일정 조회 최적화 |
| **캐시** | 팀 정보, 사용자 역할 정보 | 메모리 캐시 (TTL: 5분) |
| **동시 사용자** | 단일 팀당 최대 10명 동시 사용 | 부하 테스트로 검증 |

### 8.3 보안

| 요건 | 상세 |
|------|------|
| **인증** | JWT(HS256). Access Token 만료 15분, Refresh Token 만료 7일. 로그아웃 시 서버 측 Refresh Token 무효화 필수 |
| **비밀번호** | bcrypt, salt rounds ≥ 12. 최소 8자, 영문+숫자+특수문자 권고 |
| **팀 격리** | 모든 API는 요청자의 팀 소속 여부 검증. URL의 팀 ID 파라미터는 신뢰하지 않음 |
| **CORS** | 프로덕션 배포 시 명시적 도메인 화이트리스트 설정 |
| **HTTPS** | 모든 통신은 TLS 1.2 이상으로 암호화 |
| **입력 검증** | zod 스키마로 API 레이어에서 런타임 검증 |
| **SQL Injection 방지** | Prepared Statement 사용 (ORM 또는 쿼리 빌더를 통한 파라미터 바인딩) |
| **CSRF 방지** | 상태 변경 요청은 CSRF 토큰 검증 또는 SameSite 쿠키 정책 적용 |

### 8.4 가용성

| 요건 | 상세 |
|------|------|
| **서버 가용성** | 99.0% 이상 (월 4시간 이하 다운타임) |
| **데이터 백업** | 일 1회 자동 백업, 1주일 이상 보존 |
| **장애 대응** | 심각도 P1(서비스 전체 중단): 30분 내 조치 |
| **모니터링** | CPU, 메모리, DB 연결 수 실시간 모니터링, 임계값 초과 시 알림 |

### 8.5 확장성

| 요건 | 상세 |
|------|------|
| **팀 규모** | v1 기준 팀당 최대 10명 (향후 조정 가능) |
| **데이터 증가** | 월별 메시지·일정 증가율을 감안해 DB 파티셔닝 계획 (v2) |
| **마이크로서비스** | v1은 모놀리식 구조로 시작, v2에서 필요 시 분리 |

### 8.6 준수 사항

| 항목 | 상세 |
|------|------|
| **개인정보보호** | GDPR/CCPA 준수 검토 대상 (사용자 개인정보: 이메일, 비밀번호) |
| **데이터 삭제** | 사용자 탈퇴 시 개인정보 삭제 정책 수립 필요 (v1.1+) |
| **약관** | 서비스 이용약관, 개인정보 처리방침 작성 필수 (출시 전) |

## 부록: 용어 정의 (Glossary)

| 용어 | 정의 |
|------|------|
| **팀장 (Leader)** | 팀을 생성하고 일정을 관리하는 권한을 가진 사용자. 팀원 초대, 역할 변경, 제거 권한 보유. |
| **팀원 (Member)** | 팀의 일정을 조회하고 채팅으로 변경을 요청할 수 있는 사용자. 직접 일정 생성/수정/삭제 불가. |
| **초대 (Invitation)** | 팀장이 비팀원을 팀에 추가하기 위해 발송하는 요청. 수락 시 팀원 역할 자동 부여. |
| **일정 (Schedule)** | 팀이 공유하는 일정 정보. 제목, 시작/종료 시간, 담당자, 상태 포함. |
| **채팅 (Chat)** | 팀 멤버 간 소통하는 메시지 채널. (팀 + 기준 날짜) 단위로 분리. |
| **메시지 (Message)** | 채팅방에서 사용자가 전송하는 텍스트. 삭제·수정 불가(불변성). |
| **알림 (Notification)** | 팀원의 메시지, 초대 수신/응답 등 중요 이벤트를 팀장에게 알리는 인앱 메시지. |
| **PAU (Partner Active User)** | 팀을 통해 활동하는 활성 사용자. |
| **NPS (Net Promoter Score)** | 추천 의향도를 -100 ~ +100 범위로 측정하는 지표. |
